# 关键机制

本文基于当前源码总结应用的核心运行机制，重点说明目标页面识别、悬浮窗显示与隐藏、答题解禁、休闲时刻、配置存储及服务保活之间的关系。

## 1. 总体架构

```text
系统窗口发生变化
    ↓
FloatService 接收无障碍事件
    ↓
AppStateManager 判断前台包名、目标页面和解禁状态
    ↓
FloatingWindowManager 创建、暂停、恢复或移除悬浮窗
    ↓
用户答题或使用休闲时刻
    ↓
记录解禁时间并启动恢复定时器
```

[`FloatService`](../app/src/main/java/com/book/mask/floating/FloatService.java) 是总协调器。它初始化各管理器，并把应用状态检测结果转成悬浮窗操作；具体的包名和页面判断由 [`AppStateManager`](../app/src/main/java/com/book/mask/floating/AppStateManager.java) 完成，窗口资源则由 [`FloatingWindowManager`](../app/src/main/java/com/book/mask/floating/FloatingWindowManager.java) 管理。

## 2. 权限与服务启动

应用正常工作依赖两项核心权限：

- “显示在其他应用上层”，用于创建 `TYPE_APPLICATION_OVERLAY` 窗口。
- 无障碍服务，用于读取当前窗口的包名和页面节点。

主界面启动后按顺序引导用户进入悬浮窗权限页和无障碍设置页。每项权限在一次 Activity 生命周期内只自动引导一次，防止用户拒绝后被反复拉回设置页。

权限本身不会直接启动业务逻辑。真正的运行入口是系统连接 [`FloatService`](../app/src/main/java/com/book/mask/floating/FloatService.java) 后触发的 `onServiceConnected()`。服务监听：

- `TYPE_WINDOW_STATE_CHANGED`
- `TYPE_WINDOW_CONTENT_CHANGED`

无障碍配置声明了 `canRetrieveWindowContent=true`，因此可以递归读取当前页面的文字和内容描述。

## 3. 目标应用与页面识别

### 3.1 包名识别

前台包名有两个来源：

1. 无障碍窗口状态事件，负责及时响应切换。
2. 每 2 秒读取一次活动根窗口，补偿可能漏掉的事件。

所有包名观察最终都进入 `handleObservedPackage()`，避免事件检测和轮询采用不同规则。处理前会过滤：

- 本应用自己的包名，避免悬浮窗引发的窗口事件干扰判断。
- 已知或自动记录的输入法包名，避免键盘弹出时被判断为离开目标应用。

包名只有同时满足以下条件才算受支持：

- 存在于预置应用或自定义应用列表中。
- 该应用的监测开关已开启。

预置应用及自定义应用的增删改查集中在 [`CustomAppManager`](../app/src/main/java/com/book/mask/config/CustomAppManager.java)。

### 3.2 页面关键词识别

进入受支持的应用后，服务递归遍历活动窗口的无障碍节点，优先读取节点文字，没有文字时读取 `contentDescription`，并且只接受用户当前可见的节点。

实际匹配条件是：

```java
targetWord.contains(nodeText)
```

例如目标词配置为 `推荐 精选 热点` 时，页面中出现独立的“推荐”节点即可命中；如果节点文字比配置内容更长，则不一定命中。

微信是特殊情况：只要包名为微信，就直接视为目标页面，不依赖关键词和根节点是否可用，因此效果是屏蔽整个微信应用。

### 3.3 内容检测防抖

页面内容变化通常会连续产生大量事件，因此内容检测采用：

- 页面停止变化 200ms 后执行检测。
- 连续变化时最多等待 500ms，达到上限后强制检测一次。
- 答题界面显示、休闲解禁或包名切换复核期间暂停检测。

确认进入目标包名时默认采用“先显示、后识别”的顺序：先请求显示悬浮窗，再延迟 100ms 扫描页面关键词。原因是无障碍节点递归可能阻塞主线程，如果先扫描，悬浮窗首帧也会被一起延迟。

`AppStateManager` 同时按包名记录本次进入后的最后一次关键词检测结果，以及上次离开后确定的下次进入策略。确认离开目标应用时，只有同时满足以下条件，才把该应用标记为“下次先识别、后显示”：

- 最后一次页面检测未命中目标关键词，包括普通检测和强制检测。
- 当前不处于休闲解禁状态。
- 当前没有被手动隐藏。

再次进入同一个被标记的目标应用时，不抢先显示悬浮窗，而是立即扫描页面关键词：命中后才显示或恢复悬浮窗，未命中则继续保持隐藏。新一轮进入会清空该应用上一次页面检测结果，避免把旧页面状态带入本次判断。

未被标记的应用仍采用默认的“先显示、后识别”顺序。因此首次进入、上次从目标页面离开，或上次离开时处于休闲解禁/手动隐藏状态时，遮罩仍会抢先显示；如果当前实际是非目标页面，关键词检测确认未命中后，窗口会转入临时隐藏状态。

## 4. 悬浮窗显示机制

`showFloatingWindow()` 按以下顺序执行：

1. 当前应用处于休闲解禁时直接跳过显示。
2. 尝试恢复页面或包名切换时保留的窗口。
3. 已存在正常显示的窗口时跳过重复创建。
4. inflate `floating_window_layout.xml`。
5. 创建答题管理器并绑定关闭按钮。
6. 读取当前应用的提醒文字、目标日期和解禁时长。
7. 调用 `WindowManager.addView()` 添加窗口。
8. 显示成功后暂停包名检测 500ms，结束时主动复核当前包名。

窗口使用 `TYPE_APPLICATION_OVERLAY`，默认参数为：

- `FLAG_NOT_FOCUSABLE`：普通遮罩不抢输入焦点。
- `FLAG_NOT_TOUCH_MODAL`：窗口范围外的触摸可以传给下层应用。
- `FLAG_WATCH_OUTSIDE_TOUCH`：允许感知窗口外触摸。

窗口横向覆盖整个屏幕，纵向范围由每个应用独立配置的顶部和底部偏移共同决定：

```text
窗口高度 = 屏幕高度 - 顶部偏移 - 底部偏移
```

## 5. 悬浮窗隐藏与恢复

代码中存在两类本质不同的“隐藏”。

### 5.1 正式隐藏

正式隐藏调用 `WindowManager.removeView()`，同时释放 View、答题管理器和所有临时暂停状态。下次需要显示时必须重新 inflate 布局并调用 `addView()`。

触发场景包括：

- 用户答题成功或使用休闲时刻关闭遮罩。
- 确认已经离开受支持应用。
- 临时窗口保留期到期。
- 无障碍服务销毁或窗口管理器清理。

### 5.2 暂停隐藏（暖窗口）

页面或应用只是短暂切换时，不立即移除已经绘制的 Window，而是优先执行：

```text
layoutParams.alpha = 0
layoutParams.flags += FLAG_NOT_TOUCHABLE
WindowManager.updateViewLayout(...)
```

窗口因此不可见、不可触摸，但 Window、View 和已经完成的绘制资源仍然保留。回到目标页面时，通过一次 `updateViewLayout()` 恢复原透明度和 Flags，避免重新 inflate 和 `addView()` 造成额外空档。

暖窗口不再严格绑定离开时的那个目标应用：在保留期内切到**另一个**目标应用时，也直接复用已挂起的窗口，而不是丢弃重建。复用前会在窗口仍处暂停态（透明或 INVISIBLE，用户尚看不见）时，就地把窗口重新适配到新应用——按新应用的上下偏移原地改写 `layoutParams` 几何、刷新提醒文案与解禁时长、切换答题上下文（微信免答题等逻辑随之正确）；随后恢复透明度和 Flags 让窗口可见。因为 `layoutParams` 被答题视图控制器持有引用，几何只能原地改写、不能替换对象。

如果透明隐藏失败，则回退为 `View.INVISIBLE`；恢复时对应设置为 `View.VISIBLE`。

需要注意：暖窗口期间 `isFloatingWindowVisible` 和 `Share.isFloatingWindowVisible` 仍然为 `true`。这两个字段实际表达“窗口仍挂载并受管理”，不严格等于用户当前能够看到窗口。

### 5.3 暂停原因叠加

[`WindowSuspensionState`](../app/src/main/java/com/book/mask/floating/WindowSuspensionState.java) 维护两个暂停原因：

- `PAGE_TRANSITION`：页面或应用切换。
- `SYSTEM_UI`：通知栏、系统界面等 SystemUI 窗口。

第一个暂停原因出现时才执行物理隐藏，最后一个原因解除时才真正恢复。这样可以避免页面切换与 SystemUI 状态重叠时，其中一个状态提前结束导致遮罩错误显示。

## 6. 页面与应用切换

### 6.1 同一应用内离开目标页面

关键词检测从命中变为未命中时，窗口进入页面切换暂停状态，并保留 1.5 秒：

- 保留期内重新命中同一应用，直接恢复原窗口。
- 超过保留期仍未返回，正式移除窗口。

### 6.2 离开目标应用

当检测到其他包名且悬浮窗存在时，不立即认定用户已经离开，而是：

1. 在清理当前页面状态前，按最后一次关键词检测结果、休闲解禁和手动隐藏状态，记录该应用下次进入时的显示顺序；同时保留原目标应用信息用于窗口复用。
2. 将窗口变为透明且不可触摸。
3. 暂停处理中间包名事件。
4. 300ms 后读取活动根窗口进行复核。

复核结果分为：

- 已回到原目标包名：继续暂停约 800ms，再复核一次，避开系统过渡动画的尾部。
- 是另一个目标应用：结束暂停，按新包名恢复常规检测；新应用确认进入后会直接复用这个暖窗口（重新适配几何、内容与答题上下文），而不是重建。
- 是非目标包名：结束暂停，按新包名恢复常规检测，暖窗口到期或离开时释放。
- 包名不明确：等待后续事件或轮询补偿。

包名切换的暖窗口最长保留 2 秒。如果系统的“过渡动画缩放”已关闭，则跳过 300ms 复核，直接确认离开并隐藏。

### 6.3 SystemUI

检测到 `com.android.systemui` 时使用独立策略：

1. 先继续保持遮罩 100ms。
2. 如果复核时已经回到目标应用，则保持或恢复悬浮窗。
3. 如果 SystemUI 仍然存在，才把窗口临时设为透明且不可触摸。
4. 回到目标应用后直接恢复保留窗口。

如果复核时包名为空、本应用或输入法，会在 150ms 后继续重试，避免把临时无法识别的窗口误判为真正离开。

相关时间参数集中在 [`Const`](../app/src/main/java/com/book/mask/constant/Const.java)。

## 7. 答题关闭与普通解禁

点击悬浮窗关闭按钮时，处理优先级为：

1. 存在已经预备的休闲时刻时，免答题关闭。
2. 当前应用是微信时，直接视为答题通过。
3. 其他情况显示答题界面。

[`MathChallengeManager`](../app/src/main/java/com/book/mask/challenge/MathChallengeManager.java) 负责编排题型、答案校验和关闭回调；[`ChallengeViewController`](../app/src/main/java/com/book/mask/challenge/ChallengeViewController.java) 负责界面、焦点和输入法。

答题界面显示时会：

- 延迟加载答题内容，避免增加普通悬浮窗首帧耗时。
- 隐藏顶部提醒区域。
- 移除 `FLAG_NOT_FOCUSABLE`，让输入框获取焦点。
- 强制显示键盘，并周期性维持答案输入框焦点。
- 根据键盘占用空间调整题目区域高度。

答错后显示 1 秒反馈并切换下一题；答对后显示 1 秒成功反馈，再通知 `FloatService` 执行关闭。

普通解禁关闭流程为：

1. 如果当前是每应用宽松模式，增加今日宽松关闭次数。
2. 读取本次配置的解禁时长。
3. 将关闭时间和本次时长写入 MMKV。
4. 在 `Share` 中把应用标记为手动隐藏。
5. 正式移除悬浮窗。
6. 为该应用启动独立恢复定时器。
7. 到期后清除手动隐藏标记。
8. 如果用户仍在该应用，强制重新检测页面，命中时重新显示悬浮窗。

每应用的严格/宽松模式本质上是两组可选解禁时长：

| 模式 | 可选时长 | 次数规则 |
|---|---|---|
| 严格模式 | 30、60、120 秒 | 不消耗宽松次数 |
| 宽松模式 | 10、15、20、30 分钟 | 每次关闭消耗一次每日次数 |

宽松模式的定时器到期后，会自动把该应用的解禁时长切换为最长严格时长 120 秒。

## 8. 休闲时刻

“休闲时刻”和每应用的“严格/宽松解禁时长”是两套不同机制。

用户在设置页点击开启休闲时刻时，只进入待触发（armed）状态：

- 不立即开始计时。
- 不立即消耗每日次数。
- 不提前绑定某个应用。

之后首个点击关闭悬浮窗的应用会正式激活休闲时刻：

1. 将休闲时刻绑定到该应用包名。
2. 记录结束时间并消耗一次当日次数。
3. 免答题关闭悬浮窗。
4. 清理已经排队的页面和包名检测任务。
5. 在有效期内跳过该应用的悬浮窗显示和页面检测。
6. 到期后强制重新检查当前页面。

当前实现为严格休闲和宽松休闲分别保存每日次数、有效期和绑定包名：

休闲时刻状态由 [`AppSettingsManager`](../app/src/main/java/com/book/mask/personalize/AppSettingsManager.java) 持久化。普通解禁定时器到期时，如果同一应用的休闲时刻仍有效，会把自动恢复任务顺延到休闲结束。

## 9. 题目机制

支持的题型包括算术题、混合题、推理题和英文阅读题；英文阅读目前由功能开关禁用。

- 推理题和英文阅读题优先读取内存缓存，同时异步请求新题更新缓存。
- 远程题不可用时回退到本地算术题。

因此远程请求通常影响后续题目，不会阻塞当前答题界面的显示。

## 10. 悬浮窗文字与提醒

动态文字先从 MMKV 缓存读取。使用“大模型”来源时，窗口显示后异步请求新文字并更新缓存，但请求完成后不会主动刷新当前窗口，因此新文字通常在下次创建或更新悬浮窗时显示。

## 11. 配置与运行状态边界

持久化到 MMKV 的主要数据包括：

- 自定义应用及预置应用修改。
- 每应用监测开关、关键词、窗口偏移和文字来源。
- 每应用解禁时长、关闭时间、宽松次数。
- 休闲时刻配置、每日次数、有效期和绑定包名。
- 题型、算术难度、目标日期和提醒文字。

仅保存在进程内存中的主要状态包括：

- 当前活跃应用 `Share.currentApp`。
- 当前页面是否命中。
- 每个应用本次进入后的最后一次关键词检测结果，以及下次进入是否需要先检测再显示。
- 每应用手动隐藏标记。
- 悬浮窗是否挂载。
- 正在排队的页面检测、包名复核和恢复定时器。

服务销毁时会清空这些内存状态。虽然普通关闭时间和时长已经持久化，但手动隐藏标记及 Handler 定时器不会自动完整恢复，因此服务进程重建后的运行现场不等同于销毁前状态。

## 12. 保活与清理

[`ServiceKeepAliveManager`](../app/src/main/java/com/book/mask/lifecycle/ServiceKeepAliveManager.java) 当前主要执行：

- 动态注册屏幕和用户解锁相关广播。
- 用户解锁后检查无障碍服务是否仍在运行。
- 每 30 秒检查一次服务实例状态。

无障碍服务由 Android 系统管理，检测到停止后代码只记录日志并触发回调，不能自行重新开启无障碍服务。动态注册的开机广播也只有在服务进程已经运行且接收器已注册时才能收到，因此这里属于运行状态监测和恢复辅助，不是能够强制拉起服务的完整保活方案。

`FloatService.onDestroy()` 会清理：

- 各应用恢复定时器。
- 页面检测和包名确认任务。
- 悬浮窗及答题界面。
- 屏幕广播接收器。
- 网络线程池和设备信息上报资源。
- `Share` 中的运行时应用状态。
